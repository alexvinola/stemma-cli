# v0.5.0 — Semantic Baseline

This release strengthens the semantic boundary between imported configuration,
canonical entities and provider output. Plans explain effective delivery,
preserve distinct instructions and report names that match generated skills.

## More faithful semantics

- Codex uses one effective instructions file per directory. A present
  `AGENTS.override.md` takes precedence over `AGENTS.md`; shadowed content stays
  preserved and inactive, including when the override is empty. Generated
  instruction chains report the default Codex size limit.
- Provider extensions are classified by semantic kind. Fields not written for
  a destination remain visible in diagnostics and mapping quality; security
  losses require explicit fingerprint acceptance.
- Deduplication considers only eligible active guidance with equivalent
  activation and metadata. Disabled, human-only, profile-sensitive and uncertain
  entities cannot replace enabled guidance. Text comparison is byte-for-byte:
  spaces, indentation and literal blocks are never normalized away.
- The compiler's intermediate representation has an explicit boundary and
  regression coverage for loss, activation and deterministic projection.

## Names and discovery

- Cross-provider migration reuses safe, unambiguous source names while keeping
  canonical IDs stable. Explicit profile destinations and target-native recorded
  names retain precedence. Collisions and unsafe derived names fall back to
  complete canonical IDs with `STEMMA3702`.
- Renamed skills report their effective invocation name in mappings, plans and
  explanations, including profile pins and generated skill conversions.
- Discovery counts registered configuration candidates toward its file limit,
  reports incomplete scans and models documented nested provider paths. Shared
  reader notices distinguish Kiro's reading of `AGENTS.md` from Codex import
  ownership; no second owner is silently introduced.

## Safety and documentation

- Matching outputs beneath symlinked ancestors are refused before they can be
  accepted as owned. Symlinks are not followed.
- Human-readable plans, confirmations, application results, checks and
  explanations escape terminal controls in untrusted paths and text. JSON and
  actual filesystem destinations retain their original values.
- Documentation distinguishes plain read-only planning from `plan --output-plan`,
  which writes a saved plan, and describes the disabled rolling release job.
- The [migration guide](../migration-guide.md) includes verified scoped-rule,
  naming, profile destination and `contentOverride` examples.

## Updating

Regenerate saved plans with the new build and review names, mappings and output
before applying. A destination can move from a canonical-ID name to its safe
source name, or formerly normalized duplicates can produce additional output.
Review any conflicts and pending deletions: Stemma does not delete retired
files or overwrite manual edits.

## Reference and resource limits

The investigation in [#63](https://github.com/alexvinola/stemma-cli/issues/63)
is complete as documentation. Embedded references are not automatically
rewritten, and importing a skill does not copy supporting documents, templates
or scripts. Successful `plan`/`check` results do not certify those dependencies.
Diagnostics, opt-in rewriting and explicit supporting-resource migration are
tracked separately in [#68](https://github.com/alexvinola/stemma-cli/issues/68)
for v0.6.0.
