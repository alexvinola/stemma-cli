# Embedded references and skill supporting resources — issue #63

Status: investigation complete; maintainer scheduled implementation for v0.6.0
on 2026-10-04 in [issue #68](https://github.com/alexvinola/stemma-cli/issues/68).
Baseline: `812ebfb` on `develop` (source-name preservation, #61), inspected
2026-10-04. This document records follow-up scope; it does not add rewriting,
dependency detection, resource import, or a new schema to v0.5.0.

## Accepted release scope

Complete v0.5.0 with this investigation and documentation of the current limits.
Keep body text unchanged. Do not copy auxiliary files or replace provider
directory names. Implementation is tracked separately for v0.6.0 in #68, with
subtasks for:

1. Bounded recognition and actionable diagnostics for explicit local references.
2. Opt-in rewriting using final, explicit source-to-destination mappings.
3. Explicit preservation of allowlisted skill-local documents and templates.

Start with the diagnostic grammar and policy. Mapped rewriting should
depend on that grammar and report every edit in the plan. Resource preservation
must be designed independently; rewriting a link never creates its target.
Shared repository files should remain at their existing paths. Scripts and
arbitrary source files are outside the recommended resource scope.

The maintainer authorized this follow-up and its v0.6.0 milestone in chat on
2026-10-04. The working branch contains investigation documentation only;
automatic migration is future implementation. Exact grammar, diagnostic policy,
numeric resource limits and schema design still require explicit decisions in
the implementation subtasks. Documentation and lab evidence can merge separately.

## Reproduced current behavior

The separate `stemma-cli-test` laboratory contains a small synthetic case at
`scenarios/embedded-references/`, runnable from that repository:

```sh
python3 scripts/lab.py verify --source ../stemma-cli --case embedded-references
```

It imports three Copilot files: one scoped instructions document, one skill,
and one agent. Four auxiliary files are present: a skill-local reference,
template, shared repository document, and inert workflow path fixture. The
workflow fixture is deliberately not runnable. No real repository content,
agent invocation, or referenced command is used.

The case runs a default Claude projection and a profile-pinned skill projection.
It checks discovery, entity counts, canonical content, source provenance, final
paths, unchanged bodies, repeated plans, saved-plan apply, source hashes,
absence of copied resources, replan, and `check`. Logs, plans, binary identity,
and `observations.json` are retained under the laboratory's ignored `.lab/runs/`.
A PASS characterizes existing limitations; it does not certify working links.

The relevant findings are:

- Discovery recognizes configuration paths, including `SKILL.md`, not every
  file below a skill directory. Supporting documents and templates are not
  imported as entities, extensions, or opaque blocks. The registry is in
  `internal/discovery/discovery.go`.
- Skill content and agent instructions retain the embedded links, inline path
  text, provider-specific prose, and fenced command example. The Claude exporter
  passes the resolved body to its Markdown renderer without interpreting links
  (`internal/adapters/claude/export.go`).
- `.github/instructions/python.instructions.md` projects to
  `.claude/rules/python.md`; the skill projects to
  `.claude/skills/review/SKILL.md`. Its link
  `../../instructions/python.instructions.md` is still the original spelling,
  so its destination-relative interpretation points at
  `.claude/instructions/python.instructions.md`, which is not generated.
- `reference.md` and `templates/checklist.md` also stay unchanged, although no
  supporting files appear under the generated skill directory. Their original
  files remain intact under `.github/skills/review/`.
- In the default layout, `../../../docs/release.md` still reaches the shared
  document because both skill files have the same directory depth. This is an
  accident of layout, not a guaranteed rebase. The profile variant moves the
  skill to `.claude/skills/team/custom-review/SKILL.md`: that same link no longer
  reaches `docs/release.md`, although the shared document remains intact.
- The default skill mapping currently says `exact`: that accounts for the
  modelled skill fields, not the presence or meaning of dependencies outside the IR. A green
  `check` and stable replan certify generated bytes, not reference resolution.
  The profile variant is `adapted` because its invocation name changes to
  `custom-review`; that outcome still does not describe unresolved dependencies.
- No dedicated body-reference or missing-supporting-file diagnostic is emitted.
  Other projection diagnostics may still occur for agent or provider adaptation.

These are confirmed output and discovery behaviors. The broken destination
link is a confirmed usability problem in this example. Automatic link rewriting
and supporting-resource copying are unsupported features, not implemented
features with a missing provider-prefix substitution. The evidence does not
establish complete dependency detection, nor classify every occurrence of a path
in natural language as a broken dependency.

## Representative reference classes

Relative link bases below are explicit for the synthetic examples: the directory
containing the source configuration file. Real provider runtime interpretation
of arbitrary prose and commands is not inferred from Markdown syntax.

| Class | Example in `.github/skills/review/SKILL.md` | Current result | Candidate future treatment |
| --- | --- | --- | --- |
| Migrated configuration | `[Python rules](../../instructions/python.instructions.md)` | Text unchanged; target becomes `.claude/rules/python.md` | Recognize a bounded link destination, join it to the recorded source directory, then consult actual final mappings |
| Skill-local document | `[reference](reference.md)` | Text unchanged; supporting bytes are not imported or copied | Diagnostic only until explicit resource support is approved |
| Skill-local template | `[template](templates/checklist.md)` | Same limitation | A separately selected resource may preserve its relative layout |
| Shared repository resource | `[guide](../../../docs/release.md)` | Original document stays in place | Retain its repository location; rebase only under an explicit unchanged-resource declaration |
| Relative agent link | `[rules](../instructions/python.instructions.md)` in `.github/agents/reviewer.md` | Text unchanged after agent relocation | Use the agent's own source and final output directory; never the skill's base |
| GitHub workflow | `[workflow](../../workflows/ci.yml)` | Workflow is untouched; destination-relative link may break | Never turn it into a `.claude/workflows` path; an explicitly approved rebase may point back to `.github/workflows/ci.yml` |
| Provider-specific prose | `The Copilot instructions live in` followed by a backticked path | Text retained verbatim | Leave unchanged; intent and provider semantics cannot be derived from a substring |
| Command/code example | `cat .github/instructions/python.instructions.md` in a fenced block | Text retained, never executed | Exclude from automatic edits; do not analyze or execute commands |

Even the workflow link illustrates two separate decisions: keeping the original
GitHub resource unchanged is mandatory; making a relative link reach it from a
new directory would require an explicit, reviewed rebase. Neither decision
authorizes copying, execution, or provider-name replacement.

## Options and tradeoffs

| Option | Benefit | Cost and limits | Recommendation |
| --- | --- | --- | --- |
| Documentation only | Makes present boundaries clear without altering output, fingerprints, or exit codes | Users review dependencies manually; no detection guarantee | v0.5.0 deliverable |
| Bounded diagnostics | Identifies recognized references whose projection changes or cannot be determined | Requires a specified grammar, span tracking, new stable diagnostic codes, and outcome policy; unrecognized prose remains unchecked | First separate implementation after approval |
| Explicit mapped rewriting | Can repair references to files actually projected, including renamed outputs | Needs final mappings and safe body edit locations; ambiguity, split output, and fragments must be handled | Opt-in follow-up after diagnostics |
| Resource preservation | Makes selected local documents/templates available with the generated skill | Adds resource ownership, durable bytes, bounded import, schema and transactional output contracts | Separate design and approval |

There is no justification for a global `.github` → `.claude` replacement.
GitHub workflows, issue templates, external links, and example code have meanings
independent of the generated provider layout. File suffixes, skill names, profile
pins, and collision fallback also differ from a simple prefix change.

## Proposed recognition and mapping contract

This is a proposed future contract, not behavior available in this release.

The initial grammar should recognize only inline Markdown links with a simple,
literal, unencoded local destination in imported agent-facing prose, outside
fenced and indented code. Reference-style links, HTML, images, escapes, nested
parentheses, percent encoding, URLs, query strings, variable expansion, and
provider import directives should be left unchanged unless a later grammar
explicitly supports them. A parser must define byte, line, reference-count and
nesting limits and test its supported and rejected forms. It must not scan
arbitrary source code or interpret natural language to discover dependencies.

A recognized relative destination needs an explicit base: the recorded source
file's directory, or a separately declared repository-root base. Backticked path
text must not be assumed to be root-relative. Hand-authored canonical content,
profile content overrides, and edited bodies with stale provenance have no
reliable implicit original base; require an explicit declaration or leave the
reference unresolved. This includes text moved between canonical entities.

Resolve `..` segments lexically against the declared base; do not open their
targets. Reject any result that escapes the workspace. Pass the resulting
repository-relative path through `workspace.NormalizeRel`, including its
post-clean prefix checks. Reject absolute paths, backslashes, drive/ADS syntax,
NUL, and home expansion. Supporting a relative link such as
`../../instructions/python.instructions.md` does not permit traversal beyond
the repository or a relaxation of generated-path validation. No symlink target
is followed, no referenced file is fetched, and no command is executed.

Build an index from **final** projection mappings and generated files:

1. Collect all entities with each `source.sourcePath`, including spans where
   available. Preserve the association to their owning content and output spans.
2. Consider profile exclusion, optimizer deduplication, activation changes,
   destination pins and collision-driven renaming before determining a target.
   `SourceIndex` alone is insufficient: it maps paths to entity IDs, not final
   output paths or reference semantics.
3. If all contributing source entities are faithfully available in one final
   file, a whole-file reference without a fragment can have one candidate. Many
   entities aggregated into one destination are not inherently ambiguous. A
   source split across several destinations has no automatic whole-file target;
   neither does one partly skipped, blocked, or omitted during projection.
   Deduplicated entities need an explicit alias to retained output before they
   can count as available; their skipped mapping alone proves no destination.
4. Do not assume heading anchors survive aggregation, Markdown regeneration,
   renamed headings, or splitting. Leave fragments unresolved until target
   anchor semantics are modelled and validated; do not blindly retain `#anchor`.
5. For each owning entity's final file, compute the new relative spelling to
   the unique target. If that entity contributes to several output files, each
   output needs its own base and edit record. Do not mutate the canonical body
   into the path of one chosen provider.

Content spans in rendered output do not currently follow directly from source
spans: exporters add headings/front matter, aggregate bodies and sometimes
render JSON. A future implementation needs an explicit render association or
structured body segments. A post-render search-and-replace cannot safely
identify one occurrence when several entities share the same text.

Unresolved and ambiguous references must keep their original bytes and produce
an actionable diagnostic naming the owner, reference spelling/span, candidates
and reason, without suggesting a target that does not exist. Skipping an edit
must not imply the dependency is satisfied. Detection must describe its limited
grammar rather than claim the entire dependency graph was checked.

Rewriting should default off, be configured explicitly per target, and appear
in the plan with owner, source span, original spelling, final destination and
new spelling. Plan replay must rebuild and compare these records from current
IR/profile/mappings; saved edits are never write authority. `explain` should
show them as well. Successful meaning-preserving rewrites should be `adapted`
with an explanation. Recognized required dependencies known to be unavailable
should make the owner `lossy` with a referenced diagnostic, or `blocked` if the
approved policy requires it. Do not relabel every untouched inline path `lossy`
merely because it looks provider-specific. The exact warning/blocking policy
and diagnostic codes remain maintainer decisions.

## Separately scoped resource preservation

The current six entity types do not represent resource bytes, dependency edges,
or resource ownership. Provider extensions preserve metadata values, not files.
An opaque block preserves unmodelled content that was actually read from a
registered configuration file; it is not a generic archive of a skill directory.

The recommended first resource design would use an explicit allowlist of
skill-local UTF-8 documents/templates, not recursive discovery of arbitrary
files. Define each resource's stable identity, owning skill(s), relative path,
source hash, bounded bytes, and declared reference associations. Original
provider directories are provenance only; target paths derive from the final
skill destination plus the selected local layout. Shared repository resources
remain external declarations, without copying them. Scripts, source code,
binaries, executable modes, and transitive resource discovery are non-goals.

Approval would have to settle all of these before implementation:

- A versioned provider-neutral IR/storage representation. Resource hashes and
  declarations must participate in semantic fingerprints, canonical serialization
  and saved-plan invalidation. Old projects must remain readable. References
  cannot be stored only as provider extensions if they drive portable output.
- Explicit numeric per-resource, total-byte, count, depth and reference limits,
  including the relationship to `workspace.Limits`; no unbounded recursive copy.
  File-type checks and failures must preserve or block declared input rather
  than silently skip it. These numeric limits are deliberately undecided here.
- All reads and writes through `workspace`, refusing symlinks in ancestors and
  leaves. `store` owns canonical resource layout; no other package invents it.
- Deterministic path allocation after final skill naming, with case-insensitive
  and file/directory collision checks against configuration and other resources.
  A shared resource must not silently become independently owned by two skills.
- Per-resource projection accounting in addition to exactly one mapping for
  each existing entity. A required resource unavailable in a target must affect
  the owning entity's outcome, even if its text was preserved.
- Destination ownership, untracked-file and edited-file conflict protection,
  temporary files/atomic rename/rollback/recovery for configuration and resources
  in one transaction. Existing identical foreign bytes are not blanket adoption.
- Changes proposed without moving or deleting source resources. Stale generated
  resources become `delete-proposed`, never automatically removed. Imported
  byte-identical resources, if ownership is ever granted, need the same verified
  evidence and re-import revocation rules as existing configuration files.

## Relationship to #9, #11 and #61

The code integrated on `develop` already classifies omitted provider extensions
(#9) and checks discovery completeness (#11), although their GitHub issues were
still open when consulted. Issue state alone is not implementation evidence.

- #9 reports omitted context/behavior/security extension fields and adjusts
  projection outcomes (`STEMMA3801`/`STEMMA3802`). For example, a provider
  `resources` metadata field is still an extension value: classification does
  not resolve body references or copy the files its values name.
- #11 bounds visited entries separately from recognized configuration candidates,
  detects incomplete walks, registers nested memory and reports shared-reader
  gaps. A complete scan is complete for that registry; it is not a complete
  skill-resource import or dependency audit. `--allow-incomplete-scan` does not
  authorize opening additional paths.
- #61 reuses safe source names with target-specific suffixes and deterministic
  collision fallback. It provides more useful actual mappings, but does not
  rebase body text. Consumers must use those final mappings rather than guess
  destinations from source names.

## Required future regression coverage

Retain the laboratory characterization until an approved feature deliberately
changes its expectations; then revise its explanation so a PASS has the correct
meaning. Future production coverage should include:

- Small table tests for the reference grammar, code fences/indentation, external
  URLs, fragments, escapes, source-base uncertainty, traversal and symlink refusal.
  Bounded-parser fuzzing must enforce no panic and no out-of-workspace resolution.
- Explicit target-selected goldens for mapped links, relative rebasing, profile
  pins/content overrides, safe-name reuse and collision fallback, aggregation,
  split output, skipped/blocked targets and optimizer deduplication. Keep workflow
  and command/prose examples unchanged; review `make golden` output.
- Outcome tests requiring a diagnostic for recognized dependency loss, total
  projection accounting, stable diagnostic fingerprints, and clearly limited
  detection claims.
- Resource-specific tests for allowlist boundaries, unsupported file types,
  every numeric budget, storage round trips, shared owners and collisions,
  source preservation, ownership/conflicts, rollback/recovery and re-import.
- Byte-identical same-provider behavior with rewriting disabled; deterministic
  shuffled input; rebuild rejection of stale/tampered edit or resource records;
  apply followed by a plan with no changes.
- Laboratory CLI runs that verify generated references reach actual approved
  targets and that unsupported shared/workflow paths remain in their repository
  locations. No real provider runtime compatibility is implied by these checks.

## Remaining implementation decisions

Release scope is now recorded: #63 delivers the v0.5.0 investigation and #68
tracks diagnostics, opt-in mapped rewriting and explicit document/template
preservation in v0.6.0. Its design subtasks must settle the precise grammar and
opt-in control, known-loss warning versus blocking policy, and resource
IR/storage design with numeric budgets before implementing those contracts.
This branch changes no schema or provider behavior.
